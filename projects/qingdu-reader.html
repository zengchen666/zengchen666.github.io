轻读阅读器

本地 TXT/EPUB 中文阅读器，解决编码混乱与章节识别不准这两个最烦人的问题。

2026 年 9 月 个人项目 · 独立完成 状态：v0.1.0 可运行

自己读本地小说时，下载的 TXT 经常一半是 GBK 一半是 UTF-8，打开全是乱码；章节标题格式五花八门， 目录功能基本没法用。于是做了一个桌面阅读器：先探测编码再解码，再按中文章节规则切分， 配上目录侧栏、书签和四套主题。

我独立完成了从技术选型、功能实现到打包发布的全部工作， 核心逻辑写了 188 个单元测试并全部通过。

问题与背景

现成的阅读器要么只支持 UTF-8（老 TXT 直接报废），要么把整本书当一页渲染（几 MB 的文件滚动卡死）， 要么必须装安装包。我要的是一个双击就能用、不乱码、能按章跳转的本地工具。

约束有三条：主语言必须是 Java（要贴 Java 岗位的技术栈）；不能依赖用户预装 JDK； 只能利用业余时间做，所以功能范围必须收得足够窄。

关键决策

用 JavaFX 而不是 Electron / Tauri

选了什么
Java 25 + JavaFX，纯 Java 技术栈，不引入前端工程链。
放弃了
Electron（要写前端、包体 100MB 起）、Tauri（要写 Rust）。
为什么
这个项目的定位是「能演示的 Java 桌面工程」，不是「好看的 Web 应用」。单一语言能让我把时间花在业务逻辑上，而不是维护两套构建。
代价
JavaFX 生态小，复杂样式比 CSS 难写；界面的精致度确实不如 Web 方案。

用 jlink + jpackage 打绿色包，而不是安装包

选了什么
jlink 裁剪出只含所需模块的运行时，jpackage 打成免安装目录。
放弃了
只发一个 jar（要求用户自己装 JDK）、做成 exe 安装包（要处理签名和卸载）。
为什么
使用场景是「自己用 + 给别人演示」，双击就能运行最重要。裁剪后不必让用户理解什么是 JDK。
代价
打包体积仍然不小；Windows 和 macOS 必须分别在对应系统上打一次包。

SQLite 单文件数据库，存书签、阅读进度、主题和字体设置。

我的贡献

  • 编码探测：读取文件头部字节判断实际编码（UTF-8 / GBK / UTF-16）， 探测失败时按候选编码逐个尝试解码并校验，避免整本乱码。这是整个项目里最容易出边界问题的一块。
  • 中文分章：按「第 X 章 / 卷 / 回 / 节」等常见模式识别章节边界， 兼容全角数字与空格变体，切分后生成目录树供侧栏跳转。
  • 阅读状态持久化：书签位置、全书阅读进度、主题与字号设置落库， 重开应用恢复到上次位置。进度按字符偏移计算，而不是按滚动像素，避免换字号后位置漂移。
  • 界面与交互：目录侧栏、四套主题、阅读设置面板、全书进度条、应用图标。
  • 测试与打包：为核心逻辑（编码判定、分章切分、进度换算）编写 188 个单元测试， 并用 jlink + jpackage 产出免安装包。

如果重做，会改什么

编码探测现在是「猜 + 验证」，遇到混合编码的文件仍会失败。更稳的做法是分块探测： 每读一段就重新判断，而不是只在文件头判断一次。另外界面层和业务层的耦合还是偏紧， 测试主要在 service 层，UI 层几乎没有覆盖——这是我最想重构的部分。
